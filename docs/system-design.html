Collector Growth System Design

Module design

The service is split into modules. Each module is a NestJS module with the same api / application / domain / infrastructure folders as incentive-management. We follow three rules:

  1. Each module has its own PostgreSQL schema.
  2. A module never reads another module's tables.
  3. A module calls another module only through a port.

A CI check (dependency-cruiser) fails the build if a module imports another module's domain or infrastructure folder. This keeps modules apart, so one team can work on one module, and a module can move to its own service later.

Module Schema Phase What it does Ports it calls
ingest growth_ingest 0 Reads task and user events, keeps collector status, runs the nightly catch-up job WorkLedgerPort, InboxPort
ledger growth_ledger 0 Saves each decision, weekly counts and all-time totals. Sends growth.work.recorded. OutboxPort
rules growth_rules 1 Saves rule versions, checks them, turns them on None
profile growth_profile 1 Level and level history RuleSetPort, WorkLedgerPort, InboxPort
trust growth_trust 1 Trust Score RuleSetPort, InboxPort
goals growth_goals 1 Weekly goals and the Monday job RuleSetPort, WorkLedgerPort, ProfilePort, RewardPort, InboxPort
rewards growth_rewards 1 Bonus requests and their result OutboxPort, InboxPort
platform growth_platform 0 Outbox, inbox, job runs, module switches, duplicate request records None
teams growth_teams 2 Teams and team counts WorkLedgerPort, RewardPort, InboxPort
coverage growth_coverage 3 Areas that need data, area pay WorkLedgerPort, RewardPort, InboxPort

Ports

interface WorkLedgerPort {
  record(fact: DecidedSubmission, tx: EntityManager): Promise<RecordOutcome>;
  weekStats(collectorId: string, weeks: WeekKey[]): Promise<WeekStat[]>;
  totals(collectorId: string): Promise<CollectorTotals>;
  replay(from: Date, to: Date, sink: WorkListener): Promise<void>;
}

interface WorkListener {
  readonly module: ModuleCode;
  onWorkRecorded(e: WorkRecorded, tx: EntityManager): Promise<void>;
}

interface InboxPort {
  claim(consumer: ModuleCode, externalEventId: string, tx: EntityManager): Promise<boolean>;
}

interface RuleSetPort {
  active<K extends RuleKind>(kind: K, at: Date): Promise<RuleSet<K>>;
}

interface RewardPort {
  request(r: RewardRequestInput, tx: EntityManager): Promise<RewardRequestId>;
}

interface ModuleSwitchPort {
  isOn(module: ModuleCode, collectorId: string, tenantId?: string): Promise<boolean>;
}

Each strategy has a code name and is saved in a StrategyRegistry. A rule set says which strategy code and version to use. To change behaviour, we add a new strategy and a new rule set. We never edit an old strategy, so we can always explain and recompute an old week.

Listeners do not run inside the ledger transaction. The ledger saves the work row and puts one growth.work.recorded event in the outbox. Each listener module has its own queue and its own DLQ, and handles the event in its own transaction. The tx in onWorkRecorded is that module's own transaction. A bug or a slow query in one module stops only that module's queue. Work is still saved, and the module catches up after the fix. This is also how a module moves to its own service later: its queue stays the same, only the reader moves.

Data model

We use PostgreSQL 15 or later. The service has one database, and each module has its own schema in it. Foreign keys are used only inside one schema. When a table points to a row in another module, it stores only the id, and the port checks it. Ids that come from other services (collector, task, submission) keep their original type.

Only ingest writes to the ledger. Profile, trust and goals are built from the ledger. Only goals can create a bonus request.

growth_platform also has domain_event_outbox, copied from incentive-management, and idempotency_record, like task-management's idempotencyRecord.

inbox_message is shared by all modules through InboxPort. Its key includes consumer, so each module marks the same event as handled on its own.

collector_total holds all-time counts. Levels read it, so they never need to sum years of weekly rows.

Archive. work_fact partitions older than 13 months are detached and moved to the growth_archive schema on a cheaper tablespace. They are never dropped. A rebuild reads growth_ledger.work_fact and growth_archive together, so every built table, including all-time totals and levels, can always be rebuilt from the first day.

Database design

Topic What we do Why
Normal form Tables we write to are in third normal form. We do not save goal progress. We read it from collector_week_stat by primary key. Levels read collector_total, not their own copy of the count. One number lives in one place, so two copies cannot disagree.
Ledger first work_fact only gets new rows and is never deleted. Weekly counts, totals, level, Trust Score and goals are built from it. If a formula changes or has a bug, we rebuild those tables from work_fact and growth_archive.
Keys Use the source id when there is one (submission_id, collector_id). Use uuid for rows we create. Use bigint identity for big history tables. A duplicate event hits the primary key and is skipped. Number ids keep history indexes small.
Keys on split tables work_fact key is (submission_id, decided_at). goal_instance key is (id, period_start). PostgreSQL needs the partition column in every unique key. decided_at never changes for a submission, so it is still one row per submission.
CHECK constraints Every status, amount, score, count and week start has a CHECK. Some CHECKs tie two columns together, for example status MET needs met_at. The database blocks bad data even if the code has a bug. incentive-management does the same for wallets.
Status values varchar with a CHECK, not a PostgreSQL ENUM Adding or removing a value is a simple ALTER. Removing an ENUM value is hard.
Money numeric(18,2) in ETB, with the existing MoneyColumn Same as incentive-management. No rounding errors.
Time timestamptz for moments, date for weeks. A week starts Monday 00:00 Addis Ababa time. The code computes week_start from submitted_at. Every module uses the same week.
Partitions work_fact is split by month on decided_at. goal_instance is split by quarter on period_start. A scheduled job creates new partitions ahead of time. Queries only touch recent data. Old partitions move to the archive without a slow DELETE.
Partitions later collector_week_stat, collector_total and collector_level start as normal tables. Their keys start with collector_id. We can split them by collector later without changing keys.
Indexes Indexes follow how we read data: (collector_id, week_start) with INCLUDE, and partial indexes for OPEN goals and REQUESTED rewards. Small indexes. The app's main reads come straight from the index.
No duplicates Every consumer first calls InboxPort.claim, an INSERT … ON CONFLICT DO NOTHING on (consumer, external_event_id). If no row is inserted, the event is a duplicate for that module and it stops. The claim and the module's writes and outbox rows share one transaction. RabbitMQ can deliver a message more than once. Each module still applies it once. This fixes C15.
Module isolation The ledger transaction saves only the work row, the counts and one outbox event. Each module then works in its own transaction from its own queue. A bug in one module cannot stop work from being saved or block other modules.
Safe in parallel Counters use UPDATE … SET approved_count = approved_count + 1 … RETURNING. Status changes have a condition, for example UPDATE goal_instance SET status = 'MET' … WHERE status = 'OPEN' AND target <= $count RETURNING id. Admin edits check row_version. Many workers can run at once, in any order. A goal is marked met only once.
Rules cannot change A database trigger blocks changes to config, strategy_code and version after a rule set leaves DRAFT. Every saved row keeps the rule version it used, so we can always explain past weeks.
Archive and cleanup work_fact partitions older than 13 months move to growth_archive on cheaper storage and stay readable. inbox_message rows older than 30 days are deleted every day. Counts and history are kept. The live table stays small, and we can still rebuild from the first day. The nightly catch-up looks back only 3 days, well inside 30.
Migrations TypeORM migrations run at startup under the existing lock. A change first adds the new shape, and a later release removes the old shape. Big indexes use CREATE INDEX CONCURRENTLY in their own migration. Deploys with no downtime while old and new pods run together.
Personal data We save only ids, counts and amounts. No names, phone numbers or GPS points. Phase 3 adds area names only. Less personal data to protect.

Event contracts and flows

All events go through the existing domain.events exchange with the existing envelope {routingKey, payload, emittedAt}. New events also have schemaVersion. We only add fields to an event. If we must break an event, we make a new routing key ending in .v2 and send both until every reader has moved.

Each event has a JSON Schema file in the repo of the service that sends it, at contracts/events/<routingKey>.v<schemaVersion>.json. Both sides check these in CI (see Testing), so a sender cannot change an event by mistake.

growth.reward.granted has requestId, grantId and amount. growth.reward.failed has requestId and failureCode. failureCode is one of BUDGET_EXHAUSTED, PROGRAM_INACTIVE, PROGRAM_OUT_OF_WINDOW, PLATFORM_WALLET_INSUFFICIENT, INVALID_REQUEST. incentive-management saves both in its outbox.

growth.work.recorded is sent by the ledger to the growth modules. It has schemaVersion, externalEventId (growth:work:<submissionId>), submissionId, collectorId, tenantId, outcome, reasonCode, amount, weekStart, submittedAt and decidedAt.

Flow A: a submission is approved or rejected

  1. task-management saves the decision and an outbox row in one MongoDB transaction. Its outbox job sends task.submission.decided.
  2. The ingest worker, in one transaction: claims (ingest, externalEventId) in the inbox and stops if it is a duplicate. Then it inserts the work_fact row, adds to collector_week_stat and collector_total, and puts one growth.work.recorded in the outbox. Commit.
  3. The outbox job publishes growth.work.recorded. RabbitMQ copies it to the profile, trust and goals queues.
  4. trust, in its own transaction: claims (trust, externalEventId), updates trust_week_input, and recomputes the score from the last 13 weeks.
  5. profile, in its own transaction: claims (profile, externalEventId), reads totals through WorkLedgerPort, and checks the level rules. If the level changes, it saves level_change and puts collector.level.changed and a push message in the outbox.
  6. goals, in its own transaction: claims (goals, externalEventId), reads this week's count through WorkLedgerPort, and tries the OPEN → MET update. If a row comes back, rewards saves a reward_request and puts growth.reward.requested in the outbox.
  7. If one module fails, only its own message is retried or sent to its DLQ. The saved work and the other modules are not affected.

Modules read the current count when they run, which is never lower than the count when the event was made. So the order in which modules handle events does not matter.

Flow B: a bonus is paid or refused

  1. incentive-management reads growth.reward.requested from its own queue.
  2. Transaction 1: find the active PLATFORM_GROWTH program by programCode. Call issueGrant with externalEventId, sourceRefId = requestId, grantType = PLATFORM_GROWTH and metadata.source = 'GROWTH'. Put growth.reward.granted in the outbox. Commit.
  3. If the bonus cannot be paid (budget used up, program off, outside its dates, platform wallet too low), roll back. Then in transaction 2, put growth.reward.failed with the reason in the outbox. Ack the message.
  4. For any other error, throw. The existing retry runs 3 times, then the message goes to the DLQ.
  5. If the same request comes again, issueGrant finds the existing payment by externalEventId, and we send granted again. Our service ignores a reply for a request that is already done.
  6. Our service updates reward_request only WHERE status = 'REQUESTED', then tells the collector.
  7. A cleanup job alerts if a request waits more than 24 hours. It never pays again by itself.

Flow C: the Monday goal job, split into shards

  1. The scheduler calls POST /internal/jobs/weekly-goals every Monday at 00:05 Addis Ababa time (Sunday 21:05 UTC).
  2. The API inserts a job_run row for this week. If it already exists, the week already ran, so it returns 200. If not, it inserts 64 job_shard rows and returns 202.
  3. Worker pods take shards with FOR UPDATE SKIP LOCKED and a time lease, the same way the outbox job works. Shard n has the collectors where hashtext(collector_id) mod 64 = n.
  4. For each collector in the shard: close last week's OPEN goal as MISSED or FORGIVEN. Then insert this week's goal with ON CONFLICT DO NOTHING. The goal size comes from the active GOAL rule set.
  5. Each shard sends one send-notification-to-users message. When all shards are DONE, the run is DONE.

Flow D: offline work that arrives late. Work for a week whose goal is MISSED or FORGIVEN can still meet it if it arrives within lateSyncDays after the week ends. Only in that window, the update allows MISSED → MET and FORGIVEN → MET. If a forgiven week becomes MET, the collector gets the forgiveness back.

Flow E: nightly catch-up. The scheduler calls POST /internal/jobs/reconcile. The job reads decisions from the last 3 days from task-management. Any decision whose externalEventId is not claimed by ingest goes through Flow A. Once task-management has its outbox, this job is a safety check and should find zero. We count what it finds and alert if it is above zero.

Flow F: collector status. user.archived and user.deleted update synced_collector.status. Listeners skip these collectors, and the Monday job gives them no goal.

We check input in three places

  1. Request shape. The global ValidationPipe({ transform: true, whitelist: true, forbidNonWhitelisted: true }) with class-validator DTOs. forbidNonWhitelisted is stricter than incentive-management: a wrong field name gives an error instead of being ignored.
  2. Rule meaning. Each (kind, strategy_code, config_schema_version) has its own DTO and its own checker. For example, TRAILING_AVERAGE_UPLIFT v1 checks 1 <= lookbackWeeks <= 12, 0 <= upliftPct <= 100, minTarget <= starterTarget <= maxTarget, and that every level in bonusByLevel exists in the active LEVEL rule set. We check again when the rule is turned on.
  3. Database. CHECK and unique constraints catch anything the first two miss.

Event payloads are checked with class-validator DTOs when they are read, like in incentive-management. A payload that fails the check goes to the DLQ with no retry.

Internal API keys are compared in constant time, like task-management's apiKey.middleware.ts. Errors use the shared HttpExceptionFilter and the common/response-format shape.

Key rotation. Each internal key has a current and a next value, for example SCHEDULER_API_KEY and SCHEDULER_API_KEY_NEXT. The service accepts both. To rotate: set the next value, update the caller, then move next to current and clear next. No downtime, and no shared secret lives forever.

Rate limits. Collector routes allow 60 calls a minute per collector, using @nestjs/throttler with Redis storage, so all API pods share one count. Admin routes allow 120 calls a minute per user. A blocked call gets 429 with Retry-After.

Rules we always follow

  • A rule set cannot change after it leaves DRAFT. Every saved row keeps the rule version it used.
  • We never edit a released strategy. A change is a new strategy code or version.
  • Modules use ports, never each other's tables. CI checks this.
  • Modules react to work through their own queue, never inside the ledger transaction.
  • We never delete ledger rows. Old partitions move to the archive.
  • A new column on an existing table can be empty or has a default. We remove old columns only after no running code uses them.
  • A new event field is optional and its JSON Schema is updated in the same merge request. Readers ignore fields they do not know.
  • Every feature is behind a module switch that starts off.

Open questions

# Question Why it blocks

Words used in this doc

Word What it means here
Collector A person who does tasks in the mobile app
Ledger The work_fact table. One row for each approved or rejected submission. We only add rows. We never change them.
Built table A table we fill from the ledger, like weekly counts, level or Trust Score. We can delete it and build it again from the ledger.
Rule set Settings saved as data, like goal size, bonus amount or level limits. Each change is a new version.
Strategy A small piece of code that uses a rule set, like the code that sets a weekly goal
Port A TypeScript interface one module uses to call another module
Outbox A table where we save an event in the same transaction as the data change. A background job then sends it to RabbitMQ.
Inbox A table of event ids each module already handled. We use it to skip duplicates.
DLQ Dead letter queue. Where RabbitMQ puts a message that failed too many times.
Shard One slice of a big job. Workers take slices one at a time.
Module switch An on or off setting for one feature, with a percent of collectors
Shadow mode The service runs and saves data, but the app does not show anything yet
